#### Transformers 库的任务导向设计

Hugging Face 采用任务导向（Task-based）的接口设计。虽然底层架构可能都是 Transformer，但针对不同的下游任务，模型顶层的"头"（Head）结构完全不同。`AutoModel` 系列会根据模型配置自动匹配对应的类。

| 接口名称 | 任务类型 | 适用模型 | 典型应用场景 |
|---|---|---|---|
| `AutoModelForCausalLM` | 因果语言模型 | GPT, Qwen, Llama | 生成式任务、数学推理（CoT） |
| `AutoModelForSeq2SeqLM` | 序列到序列模型 | T5, BART | 机器翻译、摘要生成 |
| `AutoModelForSequenceClassification` | 序列分类 | BERT, RoBERTa | 情感分析、违禁内容检测 |
| `AutoModelForTokenClassification` | 标记分类 | BERT, LayoutLM | 命名实体识别（NER） |

#### 模型与分词器加载

加载模型时需指定精度、内存策略和注意力实现方式，并将模型迁移到 GPU。分词器路径必须与模型完全一致，以确保词表对齐。

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

model_path = "model/Qwen2.5-Math-1.5B"

# 加载模型：启用 bf16、内存优化与 FlashAttention-2
model = AutoModelForCausalLM.from_pretrained(
    model_path,
    torch_dtype=torch.bfloat16,         # 精度：防止数学计算中梯度溢出
    low_cpu_mem_usage=True,             # 内存：防止加载时系统 RAM 爆仓
    attn_implementation="flash_attention_2", # 加速：长序列推理的必备增压
).to("cuda")

# 加载分词器：必须与模型路径完全一致，确保词表对齐
tokenizer = AutoTokenizer.from_pretrained(model_path)
```

---

#### 前向传播与损失计算

模型加载后，将一个 Batch 的数据输入模型。核心计算是将预测结果（Logits）与真实标签（Labels）进行比对，使用交叉熵损失函数。

```python
# 模拟从 Dataloader 获取的一个 Batch
input_ids = train_batch["input_ids"].to("cuda")
labels = train_batch["labels"].to("cuda")

# 前向传播：获取 logits（未经过 Softmax 的原始预测得分）
outputs = model(input_ids)
logits = outputs.logits

# 计算 Loss：使用交叉熵损失函数
# 这里的 cross_entropy 会自动处理 logits 到概率的转换
import torch.nn.functional as F
loss = F.cross_entropy(logits.view(-1, logits.size(-1)), labels.view(-1))
```

> [!TIP]
> `F.cross_entropy` 内部会先对 logits 做 `log_softmax`，再计算负对数似然损失，因此无需手动对 logits 做 Softmax。

训练结束后，必须同时保存模型权重和分词器配置，以便后续加载或部署。

output_dir = "./checkpoints/sft_model"

#### 关键参数详解

##### `torch_dtype=torch.bfloat16`：数值稳定性的护城河

在数学推理训练中，思维链（CoT）非常长，计算图复杂。FP16 精度因数值范围窄，极易在训练后期触发梯度溢出（NaN）。

BF16 的精妙之处在于：它的指数位数与 FP32 完全一致，这意味着它能表达和 FP32 一样大的数值范围。在减少 50% 显存占用的同时，能确保模型在处理复杂公式推导时不崩溃。

> [!WARNING]
> 切勿在数学推理等对数值范围敏感的任务中使用 FP16，梯度溢出风险极高。

##### `low_cpu_mem_usage=True`：解决系统内存爆仓

默认逻辑是先在 CPU 内存（RAM）中完整创建一个模型，然后再搬运到 GPU。

- **痛点**：对于 70B 级别的模型，这需要近 150GB 的 RAM。
- **优化**：开启此参数后，模型利用底层库（如 `accelerate`）直接将权重映射到 GPU 或以"空壳"方式初始化，极大地降低了对服务器内存的峰值需求。

##### `attn_implementation="flash_attention_2"`：长序列的救星

数学推理通常涉及极长的 Chain-of-Thought。

- **背景**：原生 Attention 的计算量随序列长度呈平方级 $O(n^2)$ 暴涨。
- **原理**：Flash Attention 2 通过在显存层次（SRAM/HBM）上的分块计算，将计算复杂度转化为接近线性增长。
- **收益**：不仅显著提升训练速度，还能在有限的显存里塞进更长的推理步骤（Context Window）。

#### Hugging Face 模型文件结构

以 Qwen2.5-7B 模型目录为例，大语言模型在 Hugging Face 格式下通常由三部分组成：**模型配置**（配置文件）、**分词器**（Tokenizer 设置）和**权重文件**（参数数值）。

##### `config.json`：模型的"身体构造图"

该文件定义了神经网络的结构参数。从零初始化模型时，程序会读取此文件来搭建架构。

| 字段 | 示例值 | 含义 |
|---|---|---|
| `architectures` | `["Qwen2ForCausalLM"]` | 指定加载时对应的类，`AutoModel` 据此决定调用哪个 Python 类 |
| `hidden_size` | `3584` | 每一层特征向量的维度，维度越高表达能力越细致 |
| `num_hidden_layers` | `28` | 模型深度，即 Transformer Block 的层数 |
| `num_attention_heads` | `28` | 多头注意力机制中的头数 |
| `intermediate_size` | `18944` | Transformer 内部全连接层（MLP）的中间层维度 |
| `max_position_embeddings` | `131072` | 模型理论上支持的最大上下文长度（Context Window），Qwen2.5 支持 128k |
| `model_type` | `"qwen2"` | 模型的系列名称 |
| `vocab_size` | `152064` | 词表大小，模型能识别 15.2 万个不同的 Token |
| `torch_dtype` | `"bfloat16"` | 推荐的推理/训练精度，BF16 在保留 FP32 数值范围的同时节省一半显存 |
| `rope_theta` | `1000000.0` | 旋转位置编码（RoPE）的底数，值很大是为了支持超长文本不乱码 |

##### `generation_config.json`：模型的"表现偏好"

该文件定义了模型在"预测下一个词"时的默认行为。

| 字段 | 示例值 | 含义 |
|---|---|---|
| `do_sample` | `false` | 是否开启采样；`false` 为贪婪搜索（结果固定），`true` 带随机性 |
| `max_new_tokens` | `2048` | 单次生成回答的最大长度上限 |
| `bos_token_id` / `eos_token_id` | `151643` | 句子开始和结束的特殊符号 ID，Qwen 统一使用此值 |

##### `tokenizer_config.json`：文本到数字的"转换规则"

模型只能处理数字，该文件决定了文本如何转换为数字序列。

- **`added_tokens_decoder`**：记录模型特有的特殊标记（Special Tokens）。
  - `<\|im_start\|>`：聊天模版的开始符
  - `<\|im_end\|>`：聊天模版的结束符
  - 这些标记让模型知道哪里是用户提问，哪里是自身回答
- **`chat_template`**：最关键的部分，是一段 Jinja2 模板代码，定义了多轮对话如何拼接成一长串文本。例如自动将 `{"role": "user", "content": "你好"}` 转换为 `<|im_start|>user\n你好<|im_end|>\n
