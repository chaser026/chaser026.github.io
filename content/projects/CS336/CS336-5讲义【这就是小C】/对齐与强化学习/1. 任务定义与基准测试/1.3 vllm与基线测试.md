## 一、为什么选择 vLLM

在作业一中我们手动实现了 `generate` 函数，但面对成千上万条测试数据时效率极低。vLLM 通过以下三项核心技术解决了这一瓶颈：

- **PagedAttention**：借鉴操作系统虚拟内存管理思想，以页为单位动态分配 KV Cache，极大提高显存利用率
- **Continuous Batching**：不等待整个批次完成，而是动态将新请求插入当前批次，显著提升吞吐量
- **OpenAI 兼容接口**：部署后自动提供标准 Chat Completions API，方便与现有评估脚本无缝对接

> [!TIP]
> vLLM 相比原生 HuggingFace `pipeline` 或 `generate` 的核心竞争力在于：服务端调度器 + Continuous Batching 使其在高并发场景下仍能保持高 GPU 利用率。

## 二、vLLM 的部署与配置

### 部署脚本

通过以下 Shell 脚本可快速启动推理服务：

```bash
export CUDA_VISIBLE_DEVICES='0,1' # 指定可见的 GPU 编号
vllm serve model/Qwen2.5-7B \
    --served-model-name Qwen2.5-7B-Base \ # 给模型起个别名，API 调用时使用
    --tensor-parallel-size 1 \ # 张量并行大小。若模型很大，可设为 2 在两张卡上拆分模型
    --dtype bfloat16 \ # 推理精度，推荐使用 bf16 以匹配 Qwen 2.5 的训练精度
    --gpu-memory-utilization 0.3 \ # 占用显存的比例，此处设为 50%，留余地给训练或其他进程
    --max-model-len 5000 \ # 最大上下文长度
    --host 0.0.0.0 \ # 允许外部访问
    --port 8010 # 服务端口
```

### 关键参数详解

| 参数 | 含义 | 典型取值 | 注意事项 |
|---|---|---|---|
| `--tensor-parallel-size` (TP) | 张量并行度，将模型权重切分到多张 GPU | `1`（单卡）或 `2`（双卡） | 模型较大时需设为 2，使每张卡只承担部分计算 |
| `--dtype` | 推理数据类型 | `bfloat16` | 推荐与训练精度一致，避免精度损失 |
| `--gpu-memory-utilization` | KV Cache 预分配显存比例 | `0.3`～`0.9` | 若单卡同时训练+评估，必须调低 |
| `--max-model-len` | 最大上下文长度（Token 数） | `5000` | 超过此长度的请求会被拒绝 |
| `--host` / `--port` | 服务监听地址与端口 | `0.0.0.0` / `8010` | `0.0.0.0` 允许局域网访问 |

### 深入理解张量并行（Tensor Parallelism）

> [!NOTE]
> **直观类比**：如果把模型比作一本书——
> - **流水线并行（Pipeline Parallelism）**：把书拆成前 10 章给甲读、后 10 章给乙读；
> - **张量并行（Tensor Parallelism）**：把每一页、每一行都切成两半，甲读左半行、乙读右半行，两人同时读，读完后通过通信合并出完整的一行。

在 vLLM 中，对于 Transformer 层的线性层（Linear Layers），权重矩阵会按行或按列切分。例如一个 $4096 \times 4096$ 的矩阵，在 `tensor-parallel-size 2` 时，每张 GPU 只负责 $4096 \times 2048$ 的计算。

> [!WARNING]
> `--gpu-memory-utilization` 控制的是 KV Cache 缓存池的预分配比例。vLLM 会在启动时预先划出这部分显存，若你在同一张卡上同时运行训练任务，务必将此值调低，否则会因显存不足导致 OOM。

## 三、GSM8K 基准测试实战

vLLM 服务启动后会在后台监听指定端口（如 8010），同时提供兼容 OpenAI API 标准的 Web 服务。这意味着可以使用任何支持 OpenAI 协议的客户端库来驱动推理。

### 初始化客户端与配置

```python
from openai import OpenAI

VLLM_API_URL = "http://localhost:8010/v1"
# api_key 在本地 vLLM 环境下通常不需要，但库要求必须传值，故填 "empty"
client = OpenAI(base_url=VLLM_API_URL, api_key="empty")

# MODEL_NAME 必须与 vllm serve --served-model-name 参数完全一致
MODEL_NAME = "Qwen2.5-7B-Base"
```

**关键知识点**：

- **`base_url`**：API 请求入口。通过指向本地端口，绕过 OpenAI 公网服务器，直接在本地 GPU 上运行推理
- **模型解耦**：部署（vLLM 服务端）与应用（评估脚本）完全解耦，更换后台模型无需修改前端代码

### 核心请求函数

```python
def call_api(item):
    try:
        # GSM8K 评测核心：调用 Chat Completions 接口
        response = client.chat.completions.create(
            model=MODEL_NAME, # 指定目标模型
            messages=[{"role": "user", "content": item["prompt"]}], # 传入构造好的指令
            temperature=0.0,  # 关键：设置为 0 实现"贪婪搜索"，保证结果的可复现性
            max_tokens=512,   # 给推理逻辑预留足够的生成空间
        )
        gen_text = response.choices[0].message.content # 提取生成的文本内容
        
        # 使用解析工具提取文本中的数字结果
        pred = parse_gsm8k_response(gen_text)
        
        return {
            "question": item["original_question"],
            "gold": item["gold"], # 标准答案
            "pred": pred,         # 模型预测值
            "output": gen_text,   # 原始推理链
            "is_correct": (pred == item["gold"]) # 逻辑判定
        }
    except Exception as e:
        return {"error": str(e)}
```

**代码要点深度解析**：

- **`temperature=0.0`（Greedy Search）**：基准测试中不希望模型有随机发挥空间。设为 0 使模型每次选择概率最大的 Token，这是衡量模型底座能力的公平准则
- **`max_tokens=512`**：GSM8K 是推理任务，模型必须写出完整思维链（CoT）才能得分。若设得太小（如 50），推理过程会被截断，导致模型因未写完答案而被判错。对于小学数学题，512 个 Token 足以容纳完整过程
- **`response.choices[0]`**：标准 OpenAI 回复结构。默认 `n=1` 只生成一个回复，因此直接取索引 0

### 并发吞吐量优化

在 `main` 函数中通常设置 `MAX_WORKERS = 100`。

> [!TIP]
> **为什么可以开这么大？** vLLM 服务端拥有强大的调度器（Scheduler）。当 100 个线程并发发送请求时，vLLM 不会阻塞，而是将请求放入队列，并利用 Continuous Batching 技术将不同请求动态塞进同一个算力批次。

**实战建议**：如果通过 API 压测发现 GPU 利用率仍未打满，可以继续调大 `MAX_WORKERS`。这正是 vLLM 相比原生 HuggingFace 部署的核心竞争力所在。\n
